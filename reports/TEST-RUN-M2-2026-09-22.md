## 3. Findings

Three gaps surfaced, all verified directly rather than inferred.

### 3.1 The whole-model GPU coherence gates never run in CI

| Evidence | Verified at |
|---|---|
| `#![cfg(feature = "wgpu")]` on the whole file | `crates/sapient-models/tests/wgpu_coherence.rs:13` |
| Same gate on the Whisper GPU test | `crates/sapient-models/tests/whisper_wgpu_coherence.rs:12` |
| `sapient-models` ships `default = []` | `crates/sapient-models/Cargo.toml` |
| CI passes **no** `--features` | `.github/workflows/ci.yml:71` and `:94` |

CI runs bare `cargo test --workspace` on macOS and Linux. With `wgpu` off by default,
both files compile to **empty test binaries** — they appear in the log as
`0 passed; 0 failed; 0 ignored` and pass vacuously.

This matters because these are the gates CLAUDE.md describes as the safety net for the
GPU path:

> "Coherence is the gate: … asserts `WgpuForwardEngine` logits match the CPU
> `LlamaForward` … if a kernel (RoPE axis, GQA mapping, KV-cache layout, reduction) were
> subtly wrong, the per-token logits would diverge and the model would emit token-salad."

**Nuance, stated fairly:** the *per-kernel* GPU tests (`resident.rs`, 23 of them) **do**
run in CI, because they live in `sapient-backends-wgpu`, which builds with its own
default features. So GPU kernels are covered; it is the **model-level assembly of those
kernels** that is not.

**Status: I ran them (Run 2). All 6 pass on M2/Metal.**

**Suggested fix** — add one CI step:
```yaml
- run: cargo test -p sapient-models --features wgpu -- --test-threads=1
```

### 3.2 The MLX/Metal backend test never runs in CI

`tiny_llama_metal_backend_matches_cpu_reference` is gated
`#[cfg(all(target_os = "macos", feature = "mlx"))]`
(`crates/sapient-models/tests/forward_test.rs:120`). CI's macOS job builds without `mlx`,
so the MLX-vs-CPU equivalence check runs nowhere. `forward_test.rs` reported **5** tests,
not the 6 present in the file.

Lower severity than 3.1 — MLX is an optional Apple-only build — but it is the only
automated check that the MLX engine agrees with the CPU reference, and the RoPE-axis bug
it guards against (v0.3.4) produced exactly the "every model collapses to one repeated
token" failure described in CLAUDE.md.

### 3.3 `tests/integration/mlp_test.rs` is orphaned — 3 dead tests

The root `Cargo.toml` has **no `[package]` section** (verified: 0 matches) — it is
workspace-only. A root-level `tests/` directory belongs to a *package*, not a workspace,
so cargo never compiles it. Nothing references it: `grep` for `mlp_test` / `tests/integration`
across every `.toml` and `.yml` in the repo returns **nothing**.

These 3 tests (MLP graph end-to-end on the CPU backend, exercising `sapient-ir`) have
never run. Either move the file into a member crate's `tests/` directory, or delete it.

## 5. Corrections to `C-REWRITE-FEASIBILITY.md`

That report counted tests with a static `grep` and reported **"334 test functions, 19
ignored."** The measured figures differ. The measured ones are authoritative.

**Why the static count was wrong:** the regex matched `#[test]` and `#[tokio::test]` but
**not** `#[tokio::test(flavor = "multi_thread")]` — 8 tests missed.

**Full reconciliation**, which now closes exactly:

| | Count |
|---|---:|
| Test attributes in the tree | **342** |
| − gated behind `--features wgpu` (§3.1) | −6 |
| − gated behind `--features mlx` (§3.2) | −1 |
| − orphaned in `tests/integration/` (§3.3) | −3 |
| = harness tests executed | **332** |
| + doc-tests | +4 |
| = **reported total** | **336** matches the run |

Ignored: **19** harness `#[ignore]` + **1** ignored doc-test = **20** matches the run.

**Lesson:** static grep cannot see `cfg` gates or workspace membership. The three findings
in §3 are precisely the things it was blind to — and each is a test that silently does not
run. Counting tests by running them is the only reliable method.

## 6. Does this change the C conclusion? No.

**It cannot, and it is worth being precise about why.**

These 322 tests assert **equality**, never duration or bytes. `q6_k_neon_matches_scalar`
proves the SIMD kernel computes what the scalar one does; it records nothing about how
long either took. A green suite says the engine is *correct*. It says nothing about
whether rewriting it in C would make it *faster*.

So every load-bearing claim in `C-REWRITE-FEASIBILITY.md` stands unchanged:

| Claim | Still true? | Why |
|---|---|---|
| Rust and C share the LLVM backend | yes | Property of the compilers, not of any run |
| Hot kernels already use NEON intrinsics + inline `asm!` | yes | Re-verified: `kernels/quant.rs`, 3,787 lines |
| No C in the build today | yes | Re-verified: no `build.rs`, no `.c`/`.cpp` in `crates/` |
| Decode is memory-latency-bound, not compute-bound | yes | From the repo's Pi 5 measurements — untouched by a test run |
| Gap is ~50% kernel, ~50% threading | yes | From `docs/BENCHMARKS.md` Thor decomposition |
| Biggest speed + memory wins are in Rust | yes | Q5_0 dtype; threadpool redesign |
| KleidiAI is the one real C opportunity, ARM-only | yes | Unchanged |

**One thing did shift, mildly in favour of the existing recommendation.** Ranked #3 in that
report was *"multi-row / tiled GEMM for wgpu prefill (WGSL)."* The GPU stack — 23 kernel
tests plus all 6 model-level gates — is now confirmed healthy on Apple Metal on a second
chip generation (M2, where the record was M4). Building on a verified-correct GPU path is
a safer investment than bolting a C dependency onto the CPU path.

### No new performance numbers were produced

Deliberately. Two reasons:

1. **The suite produces none.** The only perf harness in the tree,
   `crates/sapient-generate/tests/moe_bench.rs`, is `#[ignore]`d and needs Mixtral-8x7B
   Q4_K_M (~26 GB) on a 32 GB+ box. **This machine has 16 GB** — it cannot run.
2. **This is an M2; the recorded benchmarks are M4.** Different silicon, different memory
   bandwidth. Quoting M2 tok/s against the M4 table in `docs/BENCHMARKS.md` would be a
   false comparison, and memory bandwidth is exactly the variable that matters most here (§6).

**To get real numbers on this machine** (~1 GB download + a release build, ~10-15 min):

```bash
cargo build --release -p sapient-cli
./target/release/sapient bench-llm openhorizon/qwen2.5-0.5b-q4 \
    --prompt "Explain quantum entanglement in one sentence." \
    --max-tokens 50 --runs 3 --json > reports/bench-m2.json
```

That reports load time, TTFT, decode tok/s, and peak RSS. It would establish an **M2
baseline** — useful in its own right, since the repo has none — but it still would not
change the C analysis, because it measures the current engine rather than a C alternative.
The only experiment that could settle *that* is building the KleidiAI-linked variant and
A/B-ing it, gated on `repacked_engine_logits_are_bit_identical`.
